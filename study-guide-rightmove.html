Day 1 · Theory

Principles, on demand.

Say the definition and the one-line soundbite aloud before you open each card — that’s the recall rep.

KISSKeep It Simpletap to reveal

Prefer the simplest design that satisfies the requirement. Clever code is a liability — harder to read, test, and change. Reach for complexity only when a real requirement forces it.

// Nested branching → flat, readable guard
func discount(_ price: Double, isMember: Bool) -> Double {
    guard isMember else { return price }
    return price * 0.9
}

“I start with the simplest thing that works, and let tests pull me toward complexity only when needed.”

DRYDon’t Repeat Yourselftap to reveal

Every piece of knowledge should have one authoritative home. But watch for premature deduplication — incidental duplication is cheaper than the wrong abstraction. Rule of three: extract on the third occurrence.

extension Double {
    var asGBP: String { "£" + String(format: "%.0f", self) }
}

“Duplication is cheaper than the wrong abstraction — I dedupe knowledge, not coincidence.”

YAGNIYou Aren’t Gonna Need Ittap to reveal

Don’t build for hypothetical future requirements. Speculative generality adds surface area to maintain and test for value that may never arrive. Build for today’s requirement; refactor when tomorrow’s actually shows up.

“I’ll add the abstraction when a second concrete case asks for it, not before.”

S — Single ResponsibilitySOLIDtap to reveal

A type should have one reason to change. A view model that also does networking has two: UI logic and transport. Split them.

final class ListingsViewModel {       // formats state only
    private let repo: ListingsRepository
    init(repo: ListingsRepository) { self.repo = repo }
}

“One responsibility per type means one reason to touch it — easier to test, safer to change.”

O — Open / ClosedSOLIDtap to reveal

Open for extension, closed for modification. Add behaviour by adding new types, not by editing a growing switch.

protocol Discount { func apply(to price: Double) -> Double }
struct MemberDiscount: Discount {
    func apply(to p: Double) -> Double { p * 0.9 }
}
// new rule = new conformance, existing code untouched

“New behaviour as a new conformance — I don’t reopen tested code to extend it.”

L — Liskov SubstitutionSOLIDtap to reveal

A subtype must be usable anywhere its supertype is, honouring the same contract. The classic break: a Square subclass of Rectangle that ties width to height violates code expecting sides to move independently.

“A subtype that surprises callers isn’t a subtype — it honours the contract or it doesn’t belong.”

I — Interface SegregationSOLIDtap to reveal

Many small focused protocols beat one fat one. Clients shouldn’t depend on methods they never call.

protocol Readable { func read() -> Data }
protocol Writable { func write(_ d: Data) }
// a read-only client conforms to Readable alone

“Small protocols mean clients depend only on what they actually use.”

D — Dependency InversionSOLIDtap to reveal

Depend on abstractions, not concretions. High-level code shouldn’t reach for URLSession directly — inject a protocol. This is your testing seam.

protocol ListingsService { func fetch() async throws -> [Listing] }

final class ViewModel {
    private let service: ListingsService   // not URLSession
    init(service: ListingsService) { self.service = service }
}

“I inject a protocol, not a concrete type — that boundary is where my test doubles plug in.”

Separation of Concernsdesigntap to reveal

Distinct concerns live in distinct places: presentation, business rules, and data access don’t bleed into each other. This is what makes the clean layers possible and keeps each part independently testable.

“Each layer owns one concern, so I can reason about and test it in isolation.”

Clean LayersData · Domain · Presentationtap to reveal
  • Presentation (View / ViewModel) — formats state for display, handles user intent. No business rules.
  • Domain (use cases / entities) — pure business logic, framework-agnostic. Imports nothing UIKit/CoreData.
  • Data (repository / data sources) — fetching, persistence, and mapping DTO → domain.

Dependencies point inward: Presentation and Data depend on Domain; Domain depends on nothing.

“The domain sits in the middle and imports nothing — UI and data both point at it.”

Seams & Protocol Doublestestabilitytap to reveal

A seam is a place you can change behaviour without editing the code under test. Inject a protocol, then substitute a stub in tests.

struct StubService: ListingsService {
    var result: [Listing]
    func fetch() async throws -> [Listing] { result }
}

“Every dependency I inject as a protocol becomes a seam — a clean place to slot a test double.”

Value vs Referencestruct vs classtap to reveal

Structs are value types — copied on assignment, no shared mutable state, ideal for models. Classes are reference types — use when you need identity or shared mutable state (e.g. a view model). Prefer value types by default.

“Value types by default — copies don’t share state, so there’s less to reason about and less to break.”

Composition over Inheritancedesigntap to reveal

Build behaviour by composing small pieces (protocols + concrete collaborators) rather than deep class hierarchies. Composition is more flexible, avoids fragile base classes, and pairs naturally with DI.

“I compose small collaborators instead of inheriting — easier to swap, test, and reason about.”

Day 1 · Testing

Writing tests by hand.

The goal isn’t coverage — it’s showing you design code with seams and assert behaviour, not internals.

The shape of every test: AAA

Arrange inputs and doubles · Act by calling the thing · Assert the observable outcome. One logical assertion per test where you can; name tests so a failure reads like a sentence: test_clamp_belowLowerBound_returnsLower.

FIRST — what good tests are

  • Fast — milliseconds, so you run them constantly.
  • Isolated — no shared state, any order.
  • Repeatable — same result every run (no clock, no network).
  • Self-validating — pass/fail, no eyeballing.
  • Timely — written alongside the code.

Test doubles — say the right word

  • Dummy — passed to satisfy a signature, never used.
  • Stub — returns canned data (state verification).
  • Spy — records how it was called, you inspect afterward.
  • Mock — pre-set expectations; verifies interactions (behaviour verification).
  • Fake — a real but simplified implementation (e.g. in-memory store).

Behaviour over implementation

Assert through the public API — the what, not the how. Tests bound to private internals break on every refactor and stop being a safety net. If a test fails only because you renamed a private method, it was testing the wrong thing.

XCTest essentials (the interview environment)

import XCTest

final class ClampTests: XCTestCase {
    // setUp() / tearDown() for shared fixtures; one fresh instance per test
    func test_clamp_withinRange_returnsValue() {
        XCTAssertEqual(clamp(5, 0, 10), 5)   // Arrange · Act · Assert
    }
}

Reach for: XCTAssertEqual, XCTAssertTrue/False, XCTAssertNil/NotNil, XCTAssertThrowsError / XCTAssertNoThrow, XCTUnwrap (throwing unwrap), XCTAssertEqual(_,_,accuracy:) for floats, XCTFail. Async: mark the test async and await directly, or use XCTestExpectation + fulfillment(of:timeout:) for callbacks.

Worth a mention. Swift Testing (Xcode 16+) is the modern alternative: import Testing, @Test func …, #expect(…) and #require(…). If asked, note it’s the direction of travel but XCTest is still what most production suites run on.

iPad-friendly drills — copy once, work there

Coding on iPad is smoother when you’re not switching apps. So each drill below is a complete, paste-ready playground file: a tiny test harness, the type under test, and the task as comments. Tap Copy, paste into a fresh playground, write your assertions in the YOUR TESTS block, and run — no flipping back to this guide.

The harness gives you two helpers to assert with: expect(_ condition, _ message) and expectEqual(_ a, _ b, _ message). Each prints ✅/❌ as it runs, then a final tally. Reveal the solution only after you’ve had a go.

Day 2 · Architecture

Designing on a blank board.

They’ll ask you to build a system from scratch and talk through it. Structure beats brilliance — drive the conversation with a framework.

Patterns — one crisp line each

  • MVC (Apple’s) — Model / View / Controller. Honest failure mode: the controller bloats into a “Massive View Controller”.
  • MVVM — the view model exposes display-ready state and owns presentation logic, importing no UIKit. Bindings (Combine, closures, or SwiftUI @Observable) push state to the view. Highly testable.
  • MVI — a single immutable State; user Intents flow through a reducer to produce the next state. Unidirectional and predictable; more ceremony.
  • Also name-drop: Clean Architecture / use-case layering, VIPER, TCA — know they exist and their trade-offs (structure vs boilerplate).

The 4D model — your spine for the session

  1. Define requirements. Ask before drawing: functional needs, and constraints — offline support? min iOS version? auth? real-time?
  2. Design high-level. Lay the clean layers: UI/Presentation → Domain → Data, plus external services. Dependencies point inward.
  3. Dive into components. Go deep where it matters (below).
  4. Discuss trade-offs. There’s no perfect design — justify the path you chose against the one you didn’t.

Key components to go deep on

  • State management — single source of truth, unidirectional flow; model loading/loaded/empty/error as an enum.
  • Persistence — Core Data / SwiftData / SQLite / files; Keychain for secrets. Talk cache invalidation and what must survive process death.
  • Concurrency — async/await, Task, actor for data isolation, @MainActor for UI, Sendable. Never block the main thread.
  • Dependency injection — constructor injection of protocols; a composition root wires concrete types. Decoupled = testable.
  • Lifecycle — backgrounding, process death, state restoration, scene lifecycle.
  • Observability — os.Logger, crash reporting (Crashlytics/Sentry), MetricKit, analytics.
  • Image handling — async load, NSCache, downsample to the display size, cancel on cell reuse.

Trade-off prompts to have ready

  • MVVM vs MVI — testability/simplicity vs strict predictability.
  • Local DB vs in-memory cache — persistence/offline vs speed/simplicity.
  • Core Data vs SwiftData — maturity/control vs modern ergonomics.
  • Reactive (Combine) vs imperative — composability vs cognitive load.
Cross-cutting, always raise them. Performance · Security (HTTPS, no secrets in source, Keychain) · Resilience (retry, offline cache, empty/error states) · Testing (which seams you’d unit-test) · Accessibility (Dynamic Type, VoiceOver labels, contrast, tap targets).

Day 2 · Live coding playbook

Pairing, not performing.

A collaborative pair-programming session over a starter project: a local JSON file standing in for an API, plus basic UI. Process beats completion.

First five minutes — earn the rest

  1. Read the brief. Run the app. Skim the starter code structure.
  2. Ask clarifying questions and restate the requirements back. Confirm scope and priorities.
  3. State your plan aloud before typing: “I’ll model the domain, define a protocol for the data source, map the JSON into it, then drive the UI from a view model.”

Narrate the whole way

Verbalise decisions and trade-offs as you go — that’s what they’re scoring. “I’m making this a value type because… I’ll inject this as a protocol so it’s testable… I’ll keep this simple for now and note where I’d extend it.”

A reliable structure

  • Define a domain model for the problem space (strict, non-optional invariants).
  • Define a protocol for the data source — your seam.
  • Map DTO → domain safely with Codable; keep the DTO separate from the domain entity and handle missing/optional keys deliberately.
  • Drive the presentation from a view model exposing display-ready state.
  • Write one early test to prove the seam exists and you think test-first.
struct ListingDTO: Decodable { let id: Int; let price: Int?; let bedrooms: Int? }
struct Listing: Equatable { let id: Int; let price: Int; let bedrooms: Int }

protocol ListingsRepository {           // seam
    func load() async throws -> [Listing]
}
Don’t gold-plate. You won’t be asked to implement networking, persistence, or complex framework features. Mention where they’d go, then spend your time on structure, modelling, and tests. And no AI assistants — autocomplete and docs only.

Day 2 · Worked example

System design: a property-listings feed.

Rehearse this aloud end-to-end. It maps almost directly onto anything Rightmove-shaped they might hand you.

1 · Define requirements (ask, don’t assume)

  • Functional: search by area; scrollable results with photo, price, beds; pagination / infinite scroll; tap → detail; save favourites.
  • Non-functional: smooth scrolling, fast image loading, graceful on poor networks, accessible, defined min iOS version.
  • Clarify: offline support needed? auth? real-time updates? how fresh must results be?

2 · Design high-level

Presentation   SearchView ─ FeedViewModel  (loading/loaded/empty/error)
     │
Domain         SearchListings · ToggleFavourite   (pure use cases)
     │
Data           ListingsRepository
                 ├─ RemoteListingsSource  (paginated API, Codable DTOs)
                 └─ LocalCache            (favourites + last page)
ImageLoader    async fetch · NSCache · downsample · cancel-on-reuse

3 · Dive into components

  • State: one enum drives the screen — .loading / .loaded([Listing]) / .empty / .error — plus a pagination cursor.
  • Persistence: favourites must survive process death → Core Data/SwiftData; cache the last page for instant cold-start. Define invalidation.
  • Concurrency: async fetch off-main; @MainActor view model publishes state; prefetch upcoming images; cancel in-flight loads on cell reuse.
  • Images: async load → NSCache → downsample to cell size (avoid decoding full-res) → placeholder → cancellation.
  • Networking: paginated endpoint, Codable DTOs mapped to domain in the repo, typed errors, bounded retry.

4 · Discuss trade-offs

  • Core Data vs SwiftData vs a lightweight cache — control/maturity vs modern ergonomics, for the favourites store.
  • Infinite scroll vs explicit paging — UX smoothness vs data usage and predictability.
  • Aggressive image prefetch vs bandwidth on cellular.
  • MVVM vs MVI for the feed — simpler bindings vs strict, debuggable state flow.
Land the cross-cutting points. Accessibility: Dynamic Type, VoiceOver labels (“£425,000, 3 bedrooms, Edinburgh”), contrast, large tap targets. Security: HTTPS, tokens in Keychain, no secrets in source. Resilience: empty + error states, retry, offline cache. Testing: view-model unit tests with a stubbed repository; snapshot tests for the cell.
