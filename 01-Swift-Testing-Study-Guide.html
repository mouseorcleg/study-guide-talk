Anatomy of a testfrom setUp/test…

No XCTestCase subclass, no test prefix. A free function with @Test is a test. Import the Testing module and use #expect for assertions.

#expect takes any boolean expression and, on failure, prints both sides for you — no family of XCTAssertEqual / XCTAssertGreaterThan variants to remember. You write the plain comparison.

#expect vs. try #requiresoft vs. hard

This is the distinction they'll want you to articulate.

  • #expect is a soft check. It records a failure and the test keeps running — good for asserting several independent things.
  • try #require is a hard check. On failure it throws, stopping the test immediately. Use it when continuing makes no sense — above all, to unwrap an optional (it replaces XCTUnwrap).

Say it like this

"I'll require the unwrap because every assertion after it depends on a non-nil value — no point flooding the report with cascading failures. The independent checks stay as expect so one failure doesn't hide the others."

Suites & lifecyclesetUp / tearDown

A @Suite groups tests. The trick that catches XCTest people: a fresh instance of the suite is created for every test it holds, so stored properties can't leak between tests. That isolation is built in — no resetting state in setUp.

Setup goes in init() (use init() async throws if it needs to await or can fail). For teardown, most tests don't need one because each instance is thrown away. When you genuinely must clean up, make the suite a final class and use deinit:

Testing errorsXCTAssertThrowsError

Pass the error type or a specific value to #expect(throws:). To assert something doesn't throw, use Never.self.

Want to inspect the thrown error? Capture it with the trailing-closure form and assert on what you catch.

Async & callbacksXCTestExpectation

Async is first-class: mark the test async and just await. No expectations, no wait(for:timeout:).

For the old "did this callback fire?" pattern, use confirmation. It fails if the block isn't called the expected number of times.

Parameterized testsno XCTest equivalent

One of the real upgrades — run the same test over many inputs, each reported separately. Pass a collection to arguments:.

Two separate collections (arguments: a, b) run every combination — the cross product. Use zip when you want matched pairs. Handy interview distinction.

Traits & tagsXCTSkip / test plans

Traits are arguments on @Test / @Suite that control behaviour.

Record a one-off failure with Issue.record("message") (that's your XCTFail). Wrap an expected-failing block in withKnownIssue { … } so a known bug doesn't turn the suite red.

They assess "clean code principles (DRY, KISS…)" by name. Know the definitions and, more importantly, the trade-offs.

How a test is structured

Arrange · Act · Assert (a.k.a. Given · When · Then). Set up the world, do the one thing, check the outcome. Keep the "Act" a single action so a failure points at one behaviour.

Naming. A good name reads as a sentence: method → condition → expected result. e.g. withdraw_whenBalanceTooLow_throwsInsufficientFunds. The test name should tell you what broke without opening the body.

Test behaviour, not implementation. Assert on observable outcomes (return values, state, thrown errors), not private internals. Tests coupled to implementation break every refactor and stop being useful.

What makes a good unit test — FIRST
  • Fast — milliseconds. Slow tests don't get run.
  • Isolated — no dependence on other tests or shared mutable state (Swift Testing's per-test instances help here).
  • Repeatable — same result every run, any machine. No reliance on the network, the clock, or random seeds you don't control.
  • Self-validating — it passes or fails on its own; no eyeballing console output.
  • Timely — written alongside (or before) the code, while the design is still soft.

The pyramid. Lots of fast unit tests at the base, fewer integration tests, a thin cap of UI/end-to-end tests. UI tests are slow and brittle, so lean on units for coverage and reserve e2e for critical happy paths.

DRY, KISS, YAGNI — with the caveats

KISS — keep it simple. Reach for the plainest thing that satisfies the requirement; don't add layers a spec didn't ask for.

DRY — don't repeat knowledge. One rule lives in one place, so a change happens once. The nuance interviewers like: in tests, prefer DAMP over DRY — a little duplication that keeps each test readable in isolation beats a clever shared helper that hides what's being tested.

YAGNI — you aren't gonna need it. Don't build for an imagined future; it's speculative complexity you'll pay to maintain and probably delete.

The move that scores

Naming a principle is table stakes. Show judgement about its limits: "I'd extract this, but over-DRYing tests can couple them and hurt readability, so here I'd keep the two cases explicit." That's the senior signal.

SOLID — the two that unlock testing

You can recite all five, but tie them to testability — that's why they matter here.

  • S — Single Responsibility. One reason to change → small units → tests are small and focused.
  • O — Open/Closed. Extend via new types, not by editing tested code.
  • L — Liskov Substitution. A conforming type must be safely usable wherever the protocol is — which is exactly what lets a fake stand in for the real thing.
  • I — Interface Segregation. Small protocols → small, cheap fakes.
  • D — Dependency Inversion. Depend on protocols, not concretions. This is the one that makes code testable — inject a protocol and you can pass a fake in the test.
Test doubles — know the five

They may hand you a dependency to fake. Use the right word:

  • Dummy — passed to satisfy a signature, never used.
  • Stub — returns canned answers ("when asked, return this user").
  • Spy — a stub that also records how it was called, so you can assert on it afterwards.
  • Mock — pre-programmed with expectations; it fails the test if the interaction it wanted didn't happen.
  • Fake — a real, lightweight working implementation (e.g. an in-memory store standing in for a database).
Seams, DI & designing for testability

A seam is a place you can swap behaviour without editing the code under test. You create seams with dependency injection — usually constructor injection of a protocol.

Testability smells to call out if you spot them: singletons and global mutable state, work done in init, and hidden dependencies on Date(), UUID() or URLSession.shared. Each one is a seam waiting to be extracted.

Say it like this

"Before I can test this I need a seam — I'd inject the clock as a closure or protocol so the test controls 'now'. Right now it depends on the real date, which breaks Repeatable."

Syntax, at a glance

Theory, one line each

  • AAA / GWT — arrange, act (once), assert.
  • FIRST — Fast, Isolated, Repeatable, Self-validating, Timely.
  • #expect vs #require — soft (keeps going) vs hard (throws, stops; use to unwrap).
  • DRY — one home per rule; but DAMP over DRY in tests for readability.
  • KISS / YAGNI — simplest thing; don't build for imagined futures.
  • Dependency Inversion — inject protocols → drop in fakes → testable.
  • Doubles — stub (answers), spy (records), mock (verifies), fake (real-lite).
  • Seam — inject the clock / network / storage instead of calling the real thing.
